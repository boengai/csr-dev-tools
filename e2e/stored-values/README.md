# The stored-value contract

What the site may store in `localStorage`, and what each stored value reads back as. The React build and the Dioxus build are both tested against it for as long as a rollback to React is possible. It was decided in [How do saved inputs survive cutover?](https://github.com/boengai/csr-dev-tools/issues/23) ([ADR-0032](https://github.com/boengai/csr-dev-tools/blob/develop/docs/adr/0032-saved-inputs-are-read-where-they-are.md), Decision 8) and built in [Capture the stored-value contract from React](https://github.com/boengai/csr-dev-tools/issues/38).

| File | What it is |
|------|------------|
| [`keys.json`](keys.json) | **The key list.** Every key the site may write. Committed data. |
| [`golden.json`](golden.json) | **The golden values.** Generated by `capture.ts`; do not edit by hand. |
| [`seeds.ts`](seeds.ts) | The hand-written inputs: older shapes and damaged values, and the deliberate differences. |
| [`drivers.ts`](drivers.ts) | How to read and edit each saving Tool through the DOM contract. Shared by the capture and the journeys. |
| [`capture.ts`](capture.ts) | The script that drives the React build and writes `golden.json`. |
| [`contract.ts`](contract.ts) | Types and shared helpers. |
| [`../persistence.spec.ts`](../persistence.spec.ts) | The persistence journeys. |
| [`../../src/test/stored-value-contract.spec.ts`](../../src/test/stored-value-contract.spec.ts) | Checks the key list against the React source, and the golden values against the key list. |

## The key list

`keys.json` has 75 keys: issue 15's 74 ([Inventory every persisted storage key](https://github.com/boengai/csr-dev-tools/issues/15)) and `csr-dev-tools-jsonpath-evaluator`, which `main` has migrated since #30 and can write back. Codec keys are listed one by one, and each one also names the pattern it comes from (`patterns`). The eight keys that shipped once and that nothing on `main` reads are left out.

Each key has:

- `owner`: the Tool key, or `dashboard` and `settings` for the two app-wide stores.
- `reader`: how `main` reads it back. One of:
  - `fields`, `input`, `value`, `codec-source`, `markdown-table`: `readJsonStorage`, which lays the value over its default (`restoreJson`).
  - `codec-mode`: the mode must be one of the Tool's modes, or the first opens.
  - `zustand`: the Zustand `persist` envelope `{state, version}`, at `envelopeVersion`.
  - `diagram`: DB Diagram's store, restored item by item.
  - `handoff`: raw text, read once and deleted.
  - `migration-source`: an older key that a migration reads.
  - `none`: written, never read (DB Diagram's corrupt backup).
- `format`: `json`, or `text` for the two raw-text keys.

`neverSaved` lists the Tools that save no input. They have no key, apart from AES's mode key, which that entry names.

The unit spec reads every key the React source can write (its key literals, each Codec's `modeStorageKey`, `sourceKeyPrefix` and modes, the Zustand store names and the handoff channels). It fails if that set and the list differ.

## The golden values

`golden.json` has `defaults`, the value each key restores to when nothing is stored, and `entries`. Each entry is one stored state and the value it restores to:

- `stored`: the raw stored text, by key, before the Tool opens.
- `shape`: `current` (what `main` writes today), `older` (a shape a migration reads), `damaged`, or `handoff` (the Mermaid handoff, which `main` writes from DB Diagram's export; it is seeded by hand).
- `provenance`:
  - `written-by-react`: React wrote `stored` when the capture drove its UI. Every `current` entry is one.
  - `seeded`: `stored` was written by hand, in `seeds.ts`. `main` cannot write older shapes or damage.
- `expected`: what both builds restore. Except for a deliberate difference, it is captured from React, never typed.
- `deliberate` and `react`: where the Dioxus build differs on purpose (ADR-0032 Decision 4: strict by type, and U+FFFD for a lone surrogate). `deliberate` says why, `expected` is written by hand in `seeds.ts`, and `react` keeps what React restores, as JSON text. `react` is text because React keeps a lone surrogate, which no strict JSON reader accepts.
- `storageAfterOpen`: every key after the Tool opened, present only when opening it wrote something: a migration, the handoff, or the layout store writing version 2 back.
- `storageAfterWrite` (DB Diagram only): every key after each listed diagram is saved as the app loads it, then the index. It shows what a save leaves (a relationship whose table is gone is dropped) and when the corrupt backup is written.

What `expected` is, by reader:

| Reader | `expected` | How it is captured |
|--------|------------|--------------------|
| `fields`, `input`, `value`, `codec-source`, `markdown-table` | The value the Tool holds | `main`'s own `restoreJson`, imported into the running app, over the captured default. With `open`, the Tool opens (so its migration runs), and then writes back what it holds, unchanged. |
| `codec-mode` | The mode, as a string | The Tool opens, and the pressed mode button is read. |
| `zustand` | The envelope `{state: {value}, version}`, as the store writes it | The app loads, and its own store is read. |
| `diagram` | `{index, diagrams}`: the restored index, and each listed diagram as it loads | The app's own `loadDiagramIndex` and `loadDiagram`. |

Markdown Table checks its grid as one value, but not when it reads it. React holds the bag as `restoreJson` restores it, so that is what `expected` records. A grid that does not match `rows` and `cols` then shows "The saved table is damaged" in the status slot, and the first edit starts from a fresh grid (`markdown-table-generator/grid-mismatch`).

A default is what a Tool writes back, unchanged, when it opens on empty storage. For the Zustand stores and DB Diagram it is what the app reads from empty storage.

Values are compared as JSON values, not as text, so neither build is bound to the other's key order or spacing.

## The persistence journeys

`e2e/persistence.spec.ts` has one journey per saving Tool or store. Each journey:

1. seeds the golden `current` values of every key the Tool writes, with `addInitScript`, once per test;
2. opens the Tool and checks the saved input shows;
3. edits it, and checks each key then holds the restored value plus the edit, in the same shape;
4. checks that every key in storage is on the key list.

Three more journeys check the Mermaid handoff, DB Diagram's corrupt backup, and that each `neverSaved` Tool writes nothing when typed into.

The journeys follow the rules of `docs/ux/parity.md` on `develop`. They read the page only through roles, accessible names, labels, `data-slot` values and test ids, and use no library or class selector. So they run unchanged against the Dioxus build, which is the rollback proof. In the parity runs they get no retries.

## Capturing

The capture runs against the Vite dev server, because it imports the app's own restore code into the page:

```bash
pnpm dev
node e2e/stored-values/capture.ts                # or --base-url http://localhost:<port>
```

It takes about two minutes. It fixes the clock, the time zone and `Math.random` (see `environment` in `golden.json`), so two runs give the same file. Timezone Converter's default depends on the zone. The script writes nothing and lists every problem if:

- a Tool writes a key that is not on the key list;
- a listed key gets no current shape or no default;
- React keeps a lone surrogate in an entry that is not marked deliberate;
- an entry is marked deliberate but React already agrees with it, or its hand-written value holds a lone surrogate;
- a Codec's `modes` in `keys.json` differ from its driver's, or the mode it opens in is not the one its default saves.

On a dev server that has only just started, a route can compile more slowly than an `expect` timeout. Run it again.

## When to change it

- **A fix on `main` that changes a stored shape, or adds or renames a key**, updates the contract in the same pull request. Change `keys.json`, `seeds.ts` or `drivers.ts`, then run the capture again and commit `golden.json`. The unit spec fails until the key list matches the source.
- **A new deliberate difference** goes in `seeds.ts`, with its reason.
- **The Rust restore path** runs every golden entry through it, natively. It comes with the first port that saves input, and is not here. Where the Dioxus key table lives is [issue 20](https://github.com/boengai/csr-dev-tools/issues/20)'s choice: `crates/registry/src/storage.rs` (ADR-0035). Its test, that the build cannot write a key that is not on the list, compares that table with `keys.json`.

`sessionStorage` (TanStack Router's scroll positions and reload guard) and Cache Storage (the background-removal model) are not part of the contract. The Dioxus build does not carry them over (ADR-0032 Decision 10).
